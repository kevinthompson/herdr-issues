Write one issue per distinct piece of work described in `$ARGUMENTS` or the conversation. Each issue is a **hand-off**: an agent holding only that issue and the repository must be able to finish the work and know it is finished.

1. **Choose the destination.** In the repository's main checkout (the first path `git worktree list` prints, which is not the current folder when you're in a worktree):
   - **The repository's setting comes first.** When the main checkout has `.issues.json`, which `/issues:config` writes, its `tracker` decides: `local` means Markdown, `linear` means Linear with its `team` as the team, and `github` means GitHub with its `repo` (else origin's) as the repository. Without one, find the tracker as below.
   - **Markdown**: the main checkout has an `issues/` folder; read and write issues only there, never in a worktree's copy. Read `issues/README.md` and `issues/TEMPLATE.md`. They are the format's single source of truth: follow their fields, sections and ID scheme exactly. List `issues/` to find the highest existing ID.
   - **Linear**: the person asks for Linear, or `git remote get-url origin` points to the `planningcenter` GitHub organization. Load the Linear tools with ToolSearch: `list_teams`, `list_issues`, `get_issue`, `list_issue_labels`, `list_issue_statuses` and `save_issue`, prefixed `mcp__linear__` or `mcp__claude_ai_Linear__` depending on how Linear is connected on this machine. Use the team that owns the repository, for example Calendar for the calendar repo; if no team clearly owns it, ask. If the Linear tools are not available, stop and say so.
   - **GitHub**: only when the setting says so. Use the GitHub CLI against the setting's `repo`, or origin's when it names none: `gh issue list`, `gh issue view` and `gh issue create`. If `gh auth status` fails, stop and tell the person to run `/issues:config`.
   - **Neither**: ask whether to set up an `issues/` folder or use Linear, and record the answer with `/issues:config`. To set one up, ask for the ID prefix (suggest one from the repository's name, for example `AT` for away-team), then write `issues/README.md` and `issues/TEMPLATE.md` from `starter/` in this skill's folder: replace `PREFIX`/`prefix` with the prefix in its case, `VERIFY_COMMAND` with the repository's real test and build commands (checked to exist, as in step 3), and "the running program" with what the project runs in, such as the emulator or the browser. Change nothing else, so every repository's issues share one format. Commit them with the first issues.
2. **Pin down the intent.** The person decides what the work is and why; you supply everything findable. Ask only about what the conversation and the code cannot answer: the outcome they want, or a choice between approaches. Creative and product content (story, dialog, art, names, copy) comes from the person: record what they gave, and when an issue needs content they haven't given, say in the issue that they provide it.
3. **Do the legwork.** Read the code the work touches, so Context names real files, functions and earlier decisions. Read related issues and link them by ID; in Linear, search the team's open issues with `list_issues`, and in GitHub with `gh issue list --search`, so you don't file a duplicate. Take Verification commands from the repository's own Makefile, scripts or README, and check each one exists. Work out which issues must finish first, including others you are creating now.
4. **Write each issue.** Whatever the destination, an issue is finished when:
   - every acceptance criterion is a check an agent can run or observe: a test, a command's output, or named behavior in the running program;
   - for a bug, the first acceptance criterion reproduces it: a test or command that fails before the fix and passes after;
   - Out of scope names the nearby work a reader might wander into;
   - Context holds what the code doesn't say: the reason for the work and any constraint behind it.

   Scope each issue to exactly one branch and one pull request: the issue is finished when that branch merges into main, whether directly or through its pull request, and nothing of it is left over. Split work that needs more than one branch or pull request, or that has separable outcomes, into several issues joined by blockers. Never write criteria that wait on a later pull request; make that work its own issue and list it as a blocker.
   - **Markdown**: write `issues/<ID>-<slug>.md` from the template, numbering on from the highest ID. Use `status: todo` unless the person says otherwise, today's date for `created`, the branch name the README's rule gives, and `blocked_by` for blockers.
   - **Linear**: create each issue with `save_issue` in the chosen team, with a short imperative title and a description in Markdown with the sections **Context**, **Goal**, **Acceptance criteria** (as a checklist), **Out of scope** and **Verification**. Create blockers first so later issues can reference them, and record blockers as Linear blocking relations, falling back to a "Blocked by" line in the description if the relation can't be set. Leave the status at the team's default and the assignee empty unless the person says otherwise, and add labels only from the team's existing ones (`list_issue_labels`). Don't invent a branch name: Linear's `gitBranchName` is used when work starts.
   - **GitHub**: create each issue with `gh issue create --title <title> --body-file <file>`, the body written to a file in the scratchpad with the same sections as Linear's description. Create blockers first and name them in a "Blocked by #<number>" line at the end of the body. Add labels only from the repository's existing ones (`gh label list`), and leave it unassigned unless the person says otherwise.
5. **Commit** (Markdown only) the new files in one commit on main in the main checkout, scoped `issues`. Issue changes are the exception to working on a branch: check that the main checkout is on main first, and if it isn't, stop and say so.
6. **Report** each issue's ID, title and path, Linear URL or GitHub URL, and any assumption you made that the person should confirm.
