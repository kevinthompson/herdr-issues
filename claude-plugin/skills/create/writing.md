# Writing issues in the background

The `/issues:create` skill hands you this guide in a background agent, with a brief carrying the settled intent, the repository's main checkout and what `issues context` printed: the tracker, its labels and the issues whose titles resemble the request. Write one issue per distinct piece of work the brief describes. Each issue is a **hand-off**: an agent holding only that issue and the repository must be able to finish the work and know it is finished.

You can't ask the person anything. The brief settles what the work is and why; you supply everything findable. When a choice the brief doesn't settle would change an issue, make the likelier one, write the issue so it says so, and list it as an assumption in your report.

1. **Use the tracker.** Act on the brief's tracker `kind`:
   - **`linear`**: Load the Linear tools with ToolSearch: `list_issues`, `get_issue`, `list_issue_labels`, `list_issue_statuses` and `save_issue`, prefixed `mcp__linear__` or `mcp__claude_ai_Linear__` depending on how Linear is connected on this machine. Use the brief's `team`. If the Linear tools are not available, stop and report that.
   - **`github`**: Use the GitHub CLI against the brief's `repo`: `gh issue view` and `gh issue create`. The brief's labels are the repository's.
   - **`beads`**: Use the `bd` CLI in the brief's main checkout, with `bd -C <main checkout>`, since the Beads database lives in its `.beads/` folder and a worktree has none. Beads keeps its database out of git, so creating issues makes no commit.
2. **Do the legwork.** Make the reads you need in as few turns as you can, as parallel tool calls. Read the code the work touches, so Context names real files, functions and earlier decisions. Read the brief's similar issues that might be the same work or related to it, and link related ones by ID; when one already covers the work, don't file a duplicate: report it instead. In Linear, also search the team's open issues with `list_issues`, since `issues context` lists only the team's default list. Take Verification commands from the repository's own Makefile, scripts or README, and check each one exists. Work out which issues must finish first, including others you are creating now.
3. **Write each issue.** Whatever the destination, an issue is finished when:
   - every acceptance criterion is a check an agent can run or observe: a test, a command's output, or named behavior in the running program;
   - for a bug, the first acceptance criterion reproduces it: a test or command that fails before the fix and passes after;
   - Out of scope names the nearby work a reader might wander into;
   - Context holds what the code doesn't say: the reason for the work and any constraint behind it;
   - each paragraph and list item is one line, never hard-wrapped, since GitHub keeps every line break.

   Creative and product content (story, dialog, art, names, copy) comes from the person: record what the brief gives, and when an issue needs content it doesn't give, say in the issue that the person provides it.

   Scope each issue to exactly one branch and one pull request: the issue is finished when that branch merges into main, whether directly or through its pull request, and nothing of it is left over. Split work that needs more than one branch or pull request, or that has separable outcomes, into several issues joined by blockers. Never write criteria that wait on a later pull request; make that work its own issue and list it as a blocker.
   - **Linear**: create each issue with `save_issue` in the brief's team, with a short imperative title and a description in Markdown with the sections **Context**, **Goal**, **Acceptance criteria** (as a checklist), **Out of scope** and **Verification**. Create blockers first so later issues can reference them, and record blockers as Linear blocking relations, falling back to a "Blocked by" line in the description if the relation can't be set. Leave the status at the team's default and the assignee empty unless the brief says otherwise, and add labels only from the team's existing ones (`list_issue_labels`). Don't invent a branch name: Linear's `gitBranchName` is used when work starts.
   - **GitHub**: create each issue with `gh issue create --repo <repo> --title <title> --body-file <file>`, the body written to a file in the scratchpad with the same sections as Linear's description. Create blockers first, and record each one as a GitHub issue dependency, which the issues panel reads: `gh api -X POST repos/<owner>/<name>/issues/<number>/dependencies/blocked_by -F issue_id=<id>`, where `<id>` is the blocker's numeric ID from `gh api repos/<owner>/<name>/issues/<blocker number> --jq .id`, not its number. Don't write "Blocked by" lines in the body. Add labels only from the brief's labels, and leave it unassigned unless the brief says otherwise.
   - **Beads**: create each issue with `bd -C <main checkout> create --title <title> --body-file <file> --json`, the body written to a file in the scratchpad with the same sections as Linear's description; its output's `id` is the new issue's ID. Create blockers first, and record each one as a `blocks` dependency, which the issues panel reads: `bd -C <main checkout> dep add <blocked ID> <blocker ID>`. Don't write "Blocked by" lines in the body. Leave the priority at Beads' default (P2, which the panel shows as Medium) unless the brief says otherwise, and add labels with `--labels` only when the brief names them.
4. **Report** to the session, as your final message, each issue's ID, title and Linear or GitHub URL (a Beads issue has no URL), any existing issue you found already covering part of the work, and every assumption the person should confirm.
