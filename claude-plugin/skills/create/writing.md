# Writing and filing issues

`/issues:create`, `/issues:plan` and `/issues:triage` follow this once the person has settled what the work is. It needs the repository's main checkout (the first path `git worktree list` prints) and what `issues context <words>` printed: the tracker, its labels and the issues whose titles resemble the work. Write one issue per distinct piece of work. Each issue is a **hand-off**: an agent holding only that issue and the repository must be able to finish the work and know it is finished.

The person settles what the work is and why; you supply everything findable. Don't ask again about what the conversation already settled. When a choice it didn't settle would change an issue, make the likelier one, write the issue so it says so, and list it as an assumption in the report.

1. **Use the tracker.** Act on the tracker's `kind`:
   - **`linear`**: Load the Linear tools with ToolSearch: `list_issues`, `get_issue`, `list_issue_labels`, `list_issue_statuses` and `save_issue`, prefixed `mcp__linear__` or `mcp__claude_ai_Linear__`, as the session's list of available tools shows. Use the tracker's `team`. If the Linear tools are not available, stop and say so.
   - **`github`**: Use the GitHub CLI against the tracker's `repo`: `gh issue view` and `gh issue create`. The labels `issues context` printed are the repository's.
   - **`beads`**: Use the `bd` CLI in the main checkout, with `bd -C <main checkout>`, since the Beads database lives in its `.beads/` folder and a worktree has none. Beads keeps its database out of git, so creating issues makes no commit.
2. **Do the legwork.** Make the reads you still need in as few turns as you can, as parallel tool calls, skipping what the session has already read. Read the repository's guide (its `AGENTS.md` or `CLAUDE.md`) for what it lets an agent check. Read the code the work touches, so Context names real files, functions and earlier decisions. Read the similar issues that might be the same work or related to it, and link related ones by ID; when one already covers the work, don't file a duplicate: report it instead. In Linear, also search the team's open issues with `list_issues`, since `issues context` lists only the team's default list. Take Verification commands from the repository's own Makefile, scripts or README, and check each one exists. Work out which issues must finish first, including others you are creating now.
3. **Write each issue.** Whatever the destination, an issue is finished when:
   - every acceptance criterion and Verification step is a check an agent may run or observe under the repository's guide, read in step 2: a test, a command's output, or named behavior in the running program when the guide lets an agent try it;
   - checks only the person can make, such as trying a change in the running app when the guide forbids the agent from doing so, go in a **Checks for the person** section as a plain list without checkboxes, never among the criteria or Verification, and the section is left out when there are none;
   - acceptance criteria describe only what this issue's work must achieve: the working session follows the repository's guide, so they don't restate its standing rules (tests passing, linting, comment conventions, version bumps and the like) or repeat Verification's commands, though a criterion may still name such a rule when the issue needs something the guide doesn't already require, such as a specific version bump the guide leaves to judgment;
   - for a bug, the first acceptance criterion reproduces it: a test or command that fails before the fix and passes after;
   - Out of scope names the nearby work a reader might wander into;
   - Context points at the files, functions and helpers the work touches and gives what the code doesn't say: the reason for the work and any constraint behind it; it describes how the code works today only where the reason or a constraint depends on it, since the session reads the code itself and a description goes stale when other work changes that code first;
   - when issues filed together touch the same code, Context names the sibling issue and which one is merged first, rather than describing code the sibling will change;
   - each paragraph and list item is one line, never hard-wrapped, since GitHub keeps every line break.

   Creative and product content (story, dialog, art, names, copy) comes from the person: record what they gave, and when an issue needs content they haven't given, say in the issue that the person provides it.

   Scope each issue to exactly one branch and one pull request: the issue is finished when that branch merges into main, whether directly or through its pull request, and nothing of it is left over. Split work that needs more than one branch or pull request, or that has separable outcomes, into several issues joined by blockers. Never write criteria that wait on a later pull request; make that work its own issue and list it as a blocker.

4. **File each issue**, blockers first so later issues can reference them.
   - **Linear**: create each issue with `save_issue` in the team, with a short imperative title and a description in Markdown with the sections **Context**, **Goal**, **Acceptance criteria** (as a checklist), **Out of scope**, **Verification** and, only when there are any, **Checks for the person**. Record blockers as Linear blocking relations, falling back to a "Blocked by" line in the description if the relation can't be set. Set the project and milestone the skill's destination names. Leave the status at the team's default and the assignee empty unless the person or the destination says otherwise, and add labels only from the team's existing ones (`list_issue_labels`). Don't invent a branch name: Linear's `gitBranchName` is used when work starts.
   - **GitHub**: create each issue with `gh issue create --repo <repo> --title <title> --body-file - <<'EOF'`, the body on standard input in the quoted heredoc, with the same sections as Linear's description. Record each blocker as a GitHub issue dependency, which the issues panel reads: `gh api -X POST repos/<owner>/<name>/issues/<number>/dependencies/blocked_by -F issue_id=<id>`, where `<id>` is the blocker's numeric ID from `gh api repos/<owner>/<name>/issues/<blocker number> --jq .id`, not its number. Don't write "Blocked by" lines in the body. Add labels only from the repository's labels, and leave it unassigned unless the person says otherwise.
   - **Beads**: create each issue with `bd -C <main checkout> create --title <title> --json --body-file - <<'EOF'`, the body on standard input in the quoted heredoc, with the same sections as Linear's description; its output's `id` is the new issue's ID. Record each blocker as a `blocks` dependency, which the issues panel reads: `bd -C <main checkout> dep add <blocked ID> <blocker ID>`. Don't write "Blocked by" lines in the body. Leave the priority at Beads' default (P2, which the panel shows as Medium) unless the person says otherwise, and add labels with `--labels` only when the person names them.
5. **Report** each issue's ID, title and Linear or GitHub URL (a Beads issue has no URL), any existing issue you found already covering part of the work, and every assumption the person should confirm.
