# Finishing with `onApproval: pull-request`

Read this beside `SKILL.md` when `issues setting onApproval` prints `pull-request`, or when the issue's branch already has a pull request with review on it.

1. **Review before opening.** This step runs before the session asks for approval. Run the repository's pre-pull-request review when its guide names one, such as a review skill in its `.claude/skills/`: invoke it with the Skill tool, or, when the skill can't be invoked that way, read its `SKILL.md` and follow its steps. Its summary is a step, not a stopping point: commit any files its linters auto-fixed, fix the findings the branch caused and commit those fixes, and carry straight on in the same turn. A finding that is a judgment call, or that the branch didn't cause, goes in an issue comment and in the pull request description instead. Only a finding you can't resolve without the person's decision, such as a security concern with no clear fix, stops here to ask.
2. **Open it.** Once the person approves, or straight away with `approval: auto`, push the branch and open a draft pull request, and share its URL: with a pull-request skill when the session lists one, otherwise with `gh pr create --draft`, a description following the repository's pull request template or guide when it has one. For a GitHub issue, its description says `Closes #<number>`, which links it, so the issue shows as in review and closes when the pull request merges. When the branch already has an open pull request, push the new commits to it instead, without asking.
3. **Move the issue to review.** A Linear issue with `issues status <issue ID> in-review`; a GitHub issue shows as in review once the pull request links it; a Beads issue stays `in_progress`.
4. **Wait for checks** only when `issues setting waitForChecks` prints `true`. Otherwise skip this step: the session hands off once the pull request is open, and the person follows its checks. When waiting, run `gh pr checks <number> --watch` in the background and carry on when it exits. Fix each failure the branch caused, push, and wait again. A failure the branch didn't cause, such as a test that passes on rerun or one already failing on main, goes in an issue comment instead.
5. **Review comments.** Read them (`gh pr view --comments` and `gh api repos/{owner}/{repo}/pulls/<number>/comments`) when the review decision asks for changes, the person asks about review, or the next step is to push or finish the branch, and address unresolved ones and failing checks. Never reply to a person, such as a reviewer on GitHub or a commenter on Linear, without their approval: draft each reply in chat and post it only once the person approves it. Posting your own findings as an issue comment doesn't need approval.
6. **Done only once merged.** Never mark the issue done while its pull request is open, even when every criterion is checked: it is done only once the pull request is approved and merged. When you find it merged (`gh pr view --json state,reviewDecision`), mark the issue done, unless Linear's GitHub integration or the merged pull request already did.
