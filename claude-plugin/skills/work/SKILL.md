---
name: work
description: Work an issue from start to finish, whether it lives in Linear, in GitHub Issues or in a local Beads database. Use when asked to work on, pick up, continue or finish an issue, ticket or task, or given an issue ID or Linear URL to work, for example "work on <issue ID>", "work on <issue URL>", "pick up <issue ID>" or "continue <issue ID>". To start issues in their own worktree spaces, use /issues:start.
argument-hint: <issue ID or Linear URL>
---

Work the issue named in `$ARGUMENTS` or the conversation until it is done, or until it needs a decision only the person can make.

**The `issues` CLI.** This skill runs `issues`, which `./setup` in the herdr-issues repository installs. When `command -v issues` fails, tell the person to run `./setup` from that repository, and stop.

**Outside the issue's worktree.** When the Herdr app is installed (`command -v herdr-app`) and the session isn't already in a linked worktree on the issue's branch, don't work the issue here: invoke `/issues:start <issue ID>` with the Skill tool as your first action, without loading the tracker's tools or reading the issue first, and stop once it reports. It opens the issue's worktree in its own Herdr space, where the next session works it.

**Gather context in one batch.** When the session starts in a linked worktree (its folder isn't the first path `git worktree list` prints), the Herdr panel or `issues worktree` already put it on the issue's branch. Then make every read steps 1 to 5 need in your first response, as parallel tool calls, rather than one turn at a time:
- the issue: `get_issue` and `list_comments` (Linear), `gh issue view` (GitHub), or, for Beads, whose IDs look like `<prefix>-<hash>` such as `notes-a1b`, `issues auth beads && bd -C "$(git worktree list --porcelain | sed -n '1s/^worktree //p')" show <id> --json --include-comments`;
- one shell command for the branch: `git worktree list | head -1`, `git log --oneline origin/main..HEAD`, `git diff --stat origin/main...HEAD`, and `git status --porcelain` unless the worktree's folder is under five minutes old (`[ -n "$(find . -maxdepth 0 -mmin -5)" ]`), since `issues worktree` just made it, nothing can be uncommitted, and its first status competes with the background setup;
- for a Linear or Beads issue, the current branch's pull request: `gh pr view --json number,state,url,isDraft,reviewDecision,headRefName` and `gh pr checks`, which fail harmlessly when it has none.

Then name the session's tab as step 3 says, and summarize as step 5 says. Read the full diff, review comments or the code only once the summary or the person's direction needs them.

1. **Find the issue** in the tracker `issues tracker --json` prints. If it fails, show what it printed and stop.
   - **`linear`**: Load `get_issue`, `list_comments`, `save_issue`, `list_issue_statuses` and the comment tool (`save_comment` or `create_comment`) with one ToolSearch, under the prefix the session's list of available tools shows (`mcp__claude_ai_Linear__` or `mcp__linear__`); don't guess it. If the Linear tools are not available, stop and say so. Call `get_issue` with `fields: ["title", "description", "status", "relations"]` so it leaves out the state history.
   - **`github`**: the issue's ID is `#<number>`. Read it with `gh issue view <number> --repo <repo> --json number,title,body,state,stateReason,assignees,labels,url,closedByPullRequestsReferences,comments`.
   - **`beads`**: the issue lives in the Beads database in the main checkout's `.beads/` folder, the first path `git worktree list` prints. A worktree has no `.beads/`, so run every `bd` command there with `bd -C <main checkout>`. First run `issues auth beads`; if it fails, relay the problem and fix it prints, tell the person to run `/issues:config`, and stop. Read the issue with `bd -C <main checkout> show <id> --json --include-comments`: its `description` is the body and `comments` its comments. Beads keeps its database out of git, so no Beads change makes a commit.
   - If no issue matches, stop and say so.
2. **Check it can start.** Read every blocker; a Beads issue's blockers are its `dependencies` whose `dependency_type` is `blocks`. If one is unfinished, or the issue waits on content or a decision only the person can provide, stop and ask.
3. **Name the session's Herdr tab after the issue**, so the Herdr agents list tells issue sessions apart. Do this in every session, including one that starts in the issue's worktree. Skip it without comment only when `$HC_TERMINAL_ID` is empty or `herdr-app` isn't installed. Summarize the issue's title in as few words as possible, one to three, and run `issues tab rename <issue ID> "<summary>"`. It renames only a tab nobody named (`Claude` or a number), so a name the person chose stays, and prefixes the issue ID when the tab's space isn't named after the issue (for example `#33 Tab names`).
4. **Get on the issue's branch.** In a linked worktree the session started in, that is the current branch, and the batch above already read its pull request. Elsewhere, `/issues:start` opened the issue's worktree when the Herdr app is installed.
   - Without the Herdr app, continue in the current folder on the `branch` that `issues branch <issue ID> --json` prints, which refuses an issue an unfinished issue blocks, and read its pull request as the batch above does once on it. First check whether the branch already exists, locally (`git rev-parse --verify --quiet <branch>`) or on origin (`git fetch origin <branch>`). An existing branch holds earlier work, so always continue on it; never create a second branch from main.
   - If it exists: check it out (`git switch <branch>`, which tracks origin's copy when there is no local one). In a worktree on a temporary `worktree-<name>` branch with nothing uncommitted or committed on it, switch to the existing branch and delete the temporary one (`git branch -D worktree-<name>`). If the temporary branch has its own changes or commits, or the existing branch is checked out in another worktree, stop and ask.
   - If it doesn't exist: run `git fetch origin main` and create the branch from `origin/main` (`git switch -c <branch> origin/main`); on a temporary `worktree-<name>` branch, rename it to that branch before committing.
   - If origin has the branch (`git fetch origin <branch>`) and the local branch is behind it with nothing uncommitted, fast-forward it (`git merge --ff-only origin/<branch>`). If the two have diverged, stop and ask.
   - In a box app worktree, set it up as CLAUDE.md's Worktrees section describes before running specs or the app.
5. **Catch up on work already done.** An issue that is already in progress may have commits, a pull request and review from an earlier session, another computer or a cloud agent. The person may only want to ask questions about it, so start light:
   - Read the issue's comments, what the branch already does (`git log --oneline origin/main..HEAD` and `git diff --stat origin/main...HEAD`), and its pull request's state, review decision and checks, all from the batch above.
   - Summarize where the issue stands in a few sentences and suggest the next action. If the person asked to continue the issue, go straight on to that action; otherwise stop to wait for them. People often continue an issue to review or extend the existing work, so the summary covers the pull request when there is one.
   - Read the review comments (`gh pr view --comments` and `gh api repos/{owner}/{repo}/pulls/<number>/comments`) when the review decision asks for changes, the person asks about review, or the next step is to push or finish the branch, and address unresolved review comments and failing checks.
   - Don't redo what's done or start a second branch.
6. **Mark it in progress.** Herdr's Start may already have done this, so check first.
   - **Linear**: move it to the team's In Progress state.
   - **GitHub**: in progress means open and assigned: assign the person when nobody is (`gh issue edit <number> --add-assignee @me`).
   - **Beads**: set its status to `in_progress` unless it already is (`bd -C <main checkout> update <id> --status in_progress`).
7. **Do the work.** Read the code named in Context, then meet each acceptance criterion, following CLAUDE.md's Code and Git rules and the repository's guide for writing code (named in its `AGENTS.md` or `CLAUDE.md`), or the test-first skill when it has none and has a test suite. Work independently through to step 10: don't stop for approval of commits or a pull request's description. Stay inside the issue's scope; record anything found out of scope in an issue comment instead of doing it.
8. **Keep the issue current as you go.** Record findings and decisions a later reader would need as issue comments: a Linear comment, `gh issue comment` for GitHub, or `bd -C <main checkout> comment <id> --file <file>` for Beads, with the comment written to a file in the scratchpad.
   - **GitHub**: check off the criteria in the body once, in step 10, with `gh issue edit <number> --body-file <file>`.
   - **Beads**: check off the criteria in the body once, in step 10: read the body again with `bd show`, so edits made meanwhile aren't lost, write it with the criteria checked to a file in the scratchpad, and save it with `bd -C <main checkout> update <id> --body-file <file>`.
   - **Linear**: every `save_issue` call returns the whole description, so save it once: check off all the criteria in a single call in step 10, as a `patch` replacing `- [ ]` with `- [x]`, without changing the state.
9. **Verify.** Run every step in **Verification**. When the issue has no Verification section, run the tests that cover the changed code and the repository's linters on the changed files instead. The issue is finished only when every criterion is checked and every verification step passes; report any failure with its output.
10. **Finish.** An issue is one branch and one merge, so it is done exactly when its branch lands in main. First commit any uncommitted work as CLAUDE.md's Git rules say. For Linear, also make the one `save_issue` call that checks off the criteria; for GitHub or Beads, the one body edit. A criterion only the person can check by hand, such as playing it in the running program, doesn't hold the issue open: leave it unchecked and say in an issue comment that it wasn't run. Then run `issues setting merge`, which prints how the repository's branches land in main, and follow it:
   - **`auto`**: merge the branch into main locally in the main checkout, run **Verification** again on main, then mark the issue done at once: Linear's Done state, or closed for GitHub or Beads as below.
   - **`review`**: the person reviews the change in this session before it merges. Once **Verification** passes, move a Linear issue to its In Review state (a GitHub issue keeps its status, since it shows as in review only while a pull request links it, and a Beads issue stays `in_progress`, since Beads has no review status), then stop: summarize the change with `git diff --stat main...HEAD` and what each commit on the branch does, and ask the person to approve the merge, saying they can also approve it themselves with the Merge button in the issue's view in the Herdr issues panel or by running `issues merge <issue ID>`, either of which merges the branch into main and marks the issue done. When the session finds its branch already merged into main (`git merge-base --is-ancestor HEAD main`), the person approved it that way: don't merge again, but continue from the merged state, running **Verification** on main and marking the issue done if it isn't yet. Once they approve in the session, finish as `auto` does: merge locally in the main checkout, run **Verification** again on main, and mark the issue done. If they ask for changes instead, make them, commit them, run **Verification** again, and ask again with a fresh summary.
   - **`pull-request`**: before opening the pull request, run the repository's pre-pull-request review when it has one (`.claude/skills/pre-pr/SKILL.md`, the `/pre-pr` skill): invoke it with the Skill tool, or, when the skill can't be invoked that way, read its `SKILL.md` and follow its steps, running the commands its Context section lists in place of the ones the slash command would fill in. Its summary is a step, not a stopping point: commit any files its linters auto-fixed, fix the findings the branch caused and commit those fixes, and carry straight on in the same turn. A finding that is a judgment call, or that the branch didn't cause, goes in an issue comment and in the pull request description instead. Only a finding you can't resolve without the person's decision, such as a security concern with no clear fix, stops here to ask. Then open a draft pull request with the open-pull-request skill, without asking first, and share its URL. For a GitHub issue, its description says `Closes #<number>`, which links it, so the issue shows as in review and closes when the pull request merges. Then move the issue to review: Linear's In Review state; a GitHub issue shows as in review once the pull request links it; a Beads issue stays `in_progress`. When the branch already has an open pull request, push the new commits to it instead. Then wait for the pull request's checks: run `gh pr checks <number> --watch` in the background and carry on when it exits. Fix each failure the branch caused, push, and wait again. A failure the branch didn't cause, such as a test that passes on rerun or one already failing on main, goes in an issue comment instead. Never reply to a person, such as a reviewer on GitHub or a commenter on Linear, without their approval: draft each reply in chat and post it only once the person approves it. Posting your own findings as an issue comment doesn't need approval. Never mark the issue done while its pull request is open, even when every criterion is checked: it is done only once the pull request is approved and merged. When you find it merged, in step 5 or here (`gh pr view --json state,reviewDecision`), mark the issue done (Linear's Done state, unless Linear's GitHub integration already moved it, or closed for GitHub or Beads as below).
   - For GitHub, done means closed as completed (`gh issue close <number> --reason completed`), unless merging its linked pull request already closed it.
   - For Beads, done means closed (`bd -C <main checkout> close <id>`); nothing closes it for you, since Beads doesn't see pull requests.
   - If the work turns out wrong or unnecessary, cancel the issue instead (Linear's Canceled state, `gh issue close <number> --reason "not planned"`, or `bd -C <main checkout> close <id> --reason "<why>"` for Beads, which has no canceled status) and say why in an issue comment.
11. **Confirm the worktree can close.** Never remove a Herdr worktree yourself. Run `issues setting complete`, which prints when the repository's work counts as complete. The work is complete when either:
   - nothing in the worktree is uncommitted (`git status --porcelain` is empty), and:
     - with `merged`, the branch is merged into main (`git merge-base --is-ancestor HEAD main`);
     - with `pull-request-open`, the branch is merged into main, or is pushed with no unpushed commits and has an open pull request (`gh pr view --json state,url`) whose checks pass or whose failures are recorded in an issue comment as not caused by the branch; or
   - the person explicitly canceled the work.

   If so, end your final message with this block, set apart from everything above it, filling in the issue ID, the reason, and the merge or PR result, and write nothing after it:

   ```
   ---

   ## ✅ Session finished: <issue ID>

   <one sentence: merged into main, or, with `pull-request-open`, PR open at <url>; nothing is uncommitted>

   **This session is finished. Close this worktree with cmd+shift+w.**
   ```

   Do not ask follow-up questions or offer further work in that message, so it reads clearly as the end of the session. Otherwise, list what's outstanding and keep the worktree. With `merged` and a pull request that is still open, end by saying the worktree stays until the pull request merges, and leave the issue in review; continuing the issue once it has merged finishes it in step 10.
