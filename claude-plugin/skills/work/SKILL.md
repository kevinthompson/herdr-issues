---
name: work
description: Work an issue from start to finish, whether it lives in Linear or in GitHub Issues. Use when asked to start, work on, pick up, continue or finish an issue, ticket or task, or given an issue ID or Linear URL to work, for example "start <issue URL>", "work on <issue ID>", "pick up <issue ID>" or "continue <issue ID>". Also starts several issues at once, each in its own worktree space, for example "start <ID> and <ID>" or "start the next 3 issues".
argument-hint: <issue IDs or Linear URLs, or "next <N>">
---

Work the issue named in `$ARGUMENTS` or the conversation until it is done, or until it needs a decision only the person can make.

**Starting a Linear issue from outside its worktree.** When the Herdr app is installed (`command -v herdr-app`), the issue is in Linear, and the session isn't already in a linked worktree on the issue's branch, your first action is one shell command from the repository: `wt --issue <issue ID> --claude "/issues:work <issue ID>"`. Don't load the Linear tools or read the issue first. `wt` reads the issue from Linear, takes its open pull request's branch or else Linear's, refuses it while an unfinished issue blocks it, branches an unstarted issue without a pull request from the local main without fetching, and opens the worktree space where the next session works the issue. Then stop and say the issue continues in that space; if `wt` refused or failed, say why and stop.

**Starting several issues.** When asked to start more than one issue, named or as "the next N", fan them out instead of working them here. This needs the Herdr app (`command -v herdr-app`); without it, say so and work only the first.
- For "the next N", pick the N highest-ranked actionable issues: ready to start, nothing blocking them, and not waiting on a decision or content only the person can provide. **GitHub**: open issues labeled `todo` with no assignee and no linked pull request, oldest first. **Linear**: the person's issues (`list_issues` with assignee `me`) in the team's unstarted state, by priority. When the context says which issues the Herdr issues panel lists, such as a project or one of its milestones, pick from that scope instead: its unstarted issues assigned to the person or to no one, by priority. If fewer than N qualify, start those and say so.
- For Linear issues, run `wt --issue <issue ID> --claude "/issues:work <issue ID>"` for each, one at a time, which also skips any an unfinished issue blocks. For GitHub issues, run steps 1 and 2 for each, skipping any that can't start and saying why, then `wt` as step 3 describes, with `--new` for unstarted ones. The first run that fetches origin lets the rest reuse that fetch. Don't mark the issues in progress or do any of their work here; each space's session does that.
- Then stop: list each issue with its branch, and any that were skipped or whose `wt` failed, with the reason.

**Gather context in one batch.** When the session starts in a linked worktree (its folder isn't the first path `git worktree list` prints), the Herdr panel or `wt` already put it on the issue's branch. Then make every read steps 1 to 4 need in your first response, as parallel tool calls, rather than one turn at a time:
- the issue: `get_issue` and `list_comments` (Linear), or `gh issue view` (GitHub);
- one shell command for the branch: `git worktree list | head -1`, `git log --oneline origin/main..HEAD`, `git diff --stat origin/main...HEAD`, and `git status --porcelain` unless the worktree's folder is under five minutes old (`[ -n "$(find . -maxdepth 0 -mmin -5)" ]`), since `wt` just made it, nothing can be uncommitted, and its first status competes with the background setup;
- the session's Herdr tab, with the `herdr-app ls` command in step 3's last bullet, which you then rename as that bullet says once you have the issue's title;
- for a Linear issue, the current branch's pull request: `gh pr view --json number,state,url,isDraft,reviewDecision,headRefName` and `gh pr checks`, which fail harmlessly when it has none.

Then summarize as step 4 says. Read the full diff, review comments or the code only once the summary or the person's direction needs them.

1. **Find the issue.** Get the repository's main checkout: the first path `git worktree list` prints, which is not the current folder when you're in a worktree.
   - **The repository's setting comes first.** When `~/.config/herdr-app/issues.json`, which `/issues:config` writes, has an entry for the main checkout under `repos` (keyed by path, with `~` for the home folder), its `tracker` decides: `linear` means Linear with its `team` as the team, and `github` means GitHub with its `repo` (else origin's) as the repository. Without one, find the tracker as below.
   - **Linear**: the argument is a Linear URL or ID, or `git remote get-url origin` points to the `planningcenter` GitHub organization. Load `get_issue`, `list_comments`, `save_issue`, `list_issue_statuses` and the comment tool (`save_comment` or `create_comment`) with one ToolSearch, under the prefix the session's list of available tools shows (`mcp__claude_ai_Linear__` or `mcp__linear__`); don't guess it. If the Linear tools are not available, stop and say so. Call `get_issue` with `fields: ["title", "description", "status", "gitBranchName", "relations"]` so it leaves out the state history.
   - **GitHub**: the issue's ID is `#<number>`. Read it with `gh issue view <number> --repo <repo> --json number,title,body,state,stateReason,assignees,labels,url,closedByPullRequestsReferences,comments`.
   - If no issue matches, stop and say so.
2. **Check it can start.** Read every blocker. If one is unfinished, or the issue waits on content or a decision only the person can provide, stop and ask.
3. **Get on the issue's branch.** For Linear, the branch is the head branch of the issue's open pull request in this repository, since earlier work may sit on a branch other than the one Linear suggests; without an open pull request, the issue's `gitBranchName`. For GitHub, it is the head branch of the issue's open linked pull request (`closedByPullRequestsReferences`), else `<number>-<title as a lowercase slug>`, cut to 50 characters of slug, as the Herdr panel names it. In a linked worktree the session started in, that is the current branch, and the batch above already read its pull request. Elsewhere, find the pull request with `gh pr list --state open --search <issue ID> --json number,title,headRefName`, taking the one whose title, branch or description names the issue.
   - **Open it in a Herdr worktree space** when the Herdr app is installed (`command -v herdr-app`) and the current folder is not already a linked worktree on the issue's branch. From the repository, run `wt --issue <issue ID> --claude "/issues:work <issue ID>"` for a Linear issue, as the section above says, or `wt <branch> --name <issue ID> --claude "/issues:work <issue ID>"` for a GitHub one. Add `--new` after the branch when the issue is unstarted and no pull request uses its branch: an open GitHub issue with no assignee and no linked pull request. Its branch can't be on origin yet, so `wt` skips the fetch. It reuses the branch's worktree or creates one under `~/.herdr/worktrees/` (from the local branch, else origin's copy of it, else `origin/main`, fetched unless `wt` fetched in the last minute; with `--new`, from the local `main` without fetching), opens a space on the repository's main checkout if none is open, and opens the worktree in a space nested under it with Claude working the issue; when a space already shows the worktree, it switches to that space instead. Then stop: say the issue continues in that space, and do no further work here. If `wt` fails, such as when the main checkout has the branch checked out, stop and ask.
   - Without the Herdr app, or when already in the issue's worktree, continue in the current folder. First check whether the branch already exists, locally (`git rev-parse --verify --quiet <branch>`) or on origin (`git fetch origin <branch>`). An existing branch holds earlier work, so always continue on it; never create a second branch from main.
   - If it exists: check it out (`git switch <branch>`, which tracks origin's copy when there is no local one). In a worktree on a temporary `worktree-<name>` branch with nothing uncommitted or committed on it, switch to the existing branch and delete the temporary one (`git branch -D worktree-<name>`). If the temporary branch has its own changes or commits, or the existing branch is checked out in another worktree, stop and ask.
   - If it doesn't exist: run `git fetch origin main` and create the branch from `origin/main` (`git switch -c <branch> origin/main`); on a temporary `worktree-<name>` branch, rename it to that branch before committing.
   - If origin has the branch (`git fetch origin <branch>`) and the local branch is behind it with nothing uncommitted, fast-forward it (`git merge --ff-only origin/<branch>`). If the two have diverged, stop and ask.
   - In a box app worktree, set it up as CLAUDE.md's Worktrees section describes before running specs or the app.
   - **Name the session's Herdr tab after the issue**, so the Herdr agents list tells issue sessions apart. Skip this without comment when `$HC_TERMINAL_ID` is empty or `herdr-app` isn't installed. Find the tab that holds this session's terminal, with its name and its space's name: `herdr-app ls | jq -r --arg terminal "$HC_TERMINAL_ID" '.spaces[] | .name as $space | .tabs[] | select(any(.terminals[]; .terminal == $terminal)) | [.id, .name, $space] | @tsv'`. Rename it only when its name is `Claude` or a number (an unnamed tab), so a name the person chose stays. The new name summarizes the issue's title in as few words as possible, one to three, prefixed with the issue ID and a space when the space's name isn't the issue ID (for example `#33 Tab names`). Run `herdr-app do tab.rename --id <tab ID> --name "<name>"`.
4. **Catch up on work already done.** An issue that is already in progress may have commits, a pull request and review from an earlier session, another computer or a cloud agent. The person may only want to ask questions about it, so start light:
   - Read the issue's comments, what the branch already does (`git log --oneline origin/main..HEAD` and `git diff --stat origin/main...HEAD`), and its pull request's state, review decision and checks, all from the batch above.
   - Summarize where the issue stands in a few sentences and suggest the next action. If the person asked to continue the issue, go straight on to that action; otherwise stop to wait for them. People often continue an issue to review or extend the existing work, so the summary covers the pull request when there is one.
   - Read the review comments (`gh pr view --comments` and `gh api repos/{owner}/{repo}/pulls/<number>/comments`) when the review decision asks for changes, the person asks about review, or the next step is to push or finish the branch, and address unresolved review comments and failing checks.
   - Don't redo what's done or start a second branch.
5. **Mark it in progress.** Herdr's Start may already have done this, so check first.
   - **Linear**: move it to the team's In Progress state.
   - **GitHub**: in progress means open and assigned: assign the person when nobody is (`gh issue edit <number> --add-assignee @me`).
6. **Do the work.** Read the code named in Context, then meet each acceptance criterion, following CLAUDE.md's Code and Git rules and the repository's guide for writing code (named in its `AGENTS.md` or `CLAUDE.md`), or the test-first skill when it has none and has a test suite. Work independently through to the pull request: don't stop for approval of commits or the description. Stay inside the issue's scope; record anything found out of scope in an issue comment instead of doing it.
7. **Keep the issue current as you go.** Record findings and decisions a later reader would need as issue comments: a Linear comment, or `gh issue comment` for GitHub.
   - **GitHub**: check off the criteria in the body once, in step 9, with `gh issue edit <number> --body-file <file>`.
   - **Linear**: every `save_issue` call returns the whole description, so save it once: check off all the criteria in a single call in step 9, as a `patch` replacing `- [ ]` with `- [x]`, without changing the state.
8. **Verify.** Run every step in **Verification**. When the issue has no Verification section, run the tests that cover the changed code and the repository's linters on the changed files instead. The issue is finished only when every criterion is checked and every verification step passes; report any failure with its output.
9. **Finish.** An issue is one branch and one merge, so it is done exactly when its branch lands in main. How it lands depends on the project, as CLAUDE.md's Git rules say. First commit any uncommitted work as CLAUDE.md's Git rules say. For Linear, also make the one `save_issue` call that checks off the criteria; for GitHub, the one body edit. A GitHub issue's pull request description says `Closes #<number>`, which links it, so the issue shows as in review and closes when the pull request merges.
   - **Personal project** (the person is the only contributor): merge the branch into main locally in the main checkout, run **Verification** again on main, then mark the issue done at once: Linear's Done state, or closed for GitHub as below. A criterion only the person can check by hand, such as playing it in the running program, doesn't hold the issue open: leave it unchecked and say in an issue comment that it wasn't run.
   - **Collaborative project**: before opening the pull request, run the repository's pre-pull-request review when it has one (`.claude/skills/pre-pr/SKILL.md`, the `/pre-pr` skill): invoke it with the Skill tool, or, when the skill can't be invoked that way, read its `SKILL.md` and follow its steps, running the commands its Context section lists in place of the ones the slash command would fill in. Its summary is a step, not a stopping point: commit any files its linters auto-fixed, fix the findings the branch caused and commit those fixes, and carry straight on in the same turn. A finding that is a judgment call, or that the branch didn't cause, goes in an issue comment and in the pull request description instead. Only a finding you can't resolve without the person's decision, such as a security concern with no clear fix, stops here to ask. Then open a draft pull request with the open-pull-request skill, without asking first, and share its URL; then move the issue to review: Linear's In Review state; a GitHub issue shows as in review once the pull request links it. When the branch already has an open pull request, push the new commits to it instead. Then wait for the pull request's checks: run `gh pr checks <number> --watch` in the background and carry on when it exits. Fix each failure the branch caused, push, and wait again. A failure the branch didn't cause, such as a test that passes on rerun or one already failing on main, goes in an issue comment instead. Never reply to a person, such as a reviewer on GitHub or a commenter on Linear, without their approval: draft each reply in chat and post it only once the person approves it. Posting your own findings as an issue comment doesn't need approval. Never mark the issue done while its pull request is open, even when every criterion is checked: it is done only once the pull request is approved and merged. When you find it merged, in step 4 or here (`gh pr view --json state,reviewDecision`), mark the issue done (Linear's Done state, unless Linear's GitHub integration already moved it, or closed for GitHub as below).
   - For GitHub, done means closed as completed (`gh issue close <number> --reason completed`), unless merging its linked pull request already closed it.
   - If the work turns out wrong or unnecessary, cancel the issue instead (Linear's Canceled state, or `gh issue close <number> --reason "not planned"`) and say why in an issue comment.
10. **Confirm the worktree can close.** Never remove a Herdr worktree yourself. The work is complete when either:
   - nothing in the worktree is uncommitted (`git status --porcelain` is empty), and the branch is merged into main (`git merge-base --is-ancestor HEAD main`) or is pushed with no unpushed commits and has an open pull request (`gh pr view --json state,url`) whose checks pass or whose failures are recorded in an issue comment as not caused by the branch; or
   - the person explicitly canceled the work.

   If so, end your final message with this block, set apart from everything above it, filling in the issue ID, the reason, and the merge or PR result, and write nothing after it:

   ```
   ---

   ## ✅ Session finished: <issue ID>

   <one sentence: merged into main, or PR open at <url>; nothing is uncommitted>

   **This session is finished. Close this worktree with cmd+shift+w.**
   ```

   Do not ask follow-up questions or offer further work in that message, so it reads clearly as the end of the session. Otherwise, list what's outstanding and keep the worktree.
