# Asking for approval with `approval: ask`

Read this beside `SKILL.md` when `issues setting approval` prints `ask`: the person approves the change in this session before it lands, before the branch merges into main with `onApproval: merge`, or before it's pushed and its pull request opens with `onApproval: pull-request`.

1. Once **Verification** passes, and with `onApproval: pull-request` the review in step 1 of `merge-pull-request.md` is done, move a Linear issue to in review with `issues status <issue ID> in-review`. A GitHub issue keeps its status, since it shows as in review only while a pull request links it; a Beads issue stays `in_progress`.
2. Stop and ask for approval. The session is done working until the person answers, so first run `issues complete <issue ID>` to mark its Herdr tab with ✅, skipping it without comment when `$HC_TERMINAL_ID` is empty or `herdr-app` isn't installed. Then summarize the change with `git diff --stat main...HEAD` and what each commit on the branch does, and ask the person to approve what comes next: merging the branch into main, or pushing it and opening its pull request. With `onApproval: merge`, say they can also approve it themselves with the Merge button in the issue's view in the Herdr issues panel, or by running `issues merge <issue ID>`; either merges the branch into main and marks the issue done.
3. When the session finds its branch already merged into main (`git merge-base --is-ancestor HEAD main`), the person approved it that way: don't merge again, but continue from the merged state, running **Verification** on main only when `SKILL.md` step 10 says it's needed, and marking the issue done if it isn't yet.
4. Once they approve in the session, leave the ✅ in place while the branch lands, and land it as `SKILL.md` step 10 says.
5. If they ask for changes instead, first withdraw the mark as `SKILL.md` step 12 says, then make them, commit them, run **Verification** again, and ask again with a fresh summary.
