# Checking a tracker's access

Read this beside `SKILL.md` in step 3, for the tracker chosen in step 2. Never print a secret, and never ask for one in chat: tell the person where to put it.

- **Linear**: the panel reads the API key from `"apiKey"` in `~/.config/herdr-app/linear.json`, where its setup view saves it and where other Herdr mods that call Linear read it too, or else from the `LINEAR_API_KEY` environment variable, which the panel reads from the person's login shell. Check the key is present with `issues auth linear`, which never prints it. If it fails, relay the problem and fix it prints: the person pastes the key in the panel's setup view, adds it to that file themselves as `{ "apiKey": "lin_api_…" }`, or sets `LINEAR_API_KEY` in their shell profile. Never read or print that file. Never ask for the key in chat. The skills reach Linear through its MCP server instead. When neither `mcp__linear__` nor `mcp__claude_ai_Linear__` tools are available, tell the person to add the server once for every project by running this command, suggesting the `! ` prefix so it runs in this session:

  ```sh
  claude mcp add --transport http --scope user linear https://mcp.linear.app/mcp
  ```

  Then they start a new Claude Code session, since a server added mid-session isn't available until one starts, run `/mcp`, choose `linear` and sign in to Linear in the browser window it opens. Say that a Linear connection on their Claude account at claude.ai works too.

- **GitHub**: the panel and the skills run the GitHub CLI as the person. Check `issues auth github`; if it fails, relay the problem and fix it prints, suggesting `! gh auth login` when gh isn't logged in. When gh isn't installed and the fix names install commands (`devbox global add gh`, `brew install gh`), offer to run one with AskUserQuestion, one option per command the fix names and one to install it themselves; on a yes, run that command and check again. If gh still isn't found after `devbox global add gh`, tell the person to make sure their shell profile evaluates `devbox global shellenv` and to start a new shell (and restart Claude Code from it), since devbox's global packages are on PATH only then. Then check the account can see the repository's issues (`gh issue list --repo <repo> --limit 1`).
- **Beads**: Beads needs no credentials, only the `bd` CLI and a database in the main checkout. Check both with `issues auth beads`; if it fails, relay the problem and fix it prints. When `bd` isn't installed and the fix names install commands (`devbox global add beads`, `brew install beads`), offer to run one as for gh, and check again. When the repository has no Beads database, offer with AskUserQuestion to make one, or to make it themselves; on a yes, run `issues auth beads --init`, which makes it in the main checkout as the panel's setup view does, so the database stays out of git, `bd` adds no agent instructions or git hooks, and its issue IDs start with the initials of the main checkout's folder name (`astro-escape` gives `ae-`), then checks again. It never changes a database that already exists.
